# Agent 平台候选、兼容验证与选型定案

更新日期：2026-10-26。本文对应第一阶段 K24；已完成固定版本的本地最小兼容验证并确定平台。企微、生产数据库和正式售前业务尚未实现或验收。原网关候选资料已冻结为历史，公司模型代理不属于本项目。

## 1. 第一阶段目标与顺序

当前主线为 **明确 Agent 平台选型 → 建设最小公共底座 → 开发售前 Agent 首个功能闭环**。优先复用开源平台，先围绕同一个企微售前流程比较和验证，再确定一个平台及版本；选型不是只列候选，也不以依赖清单已有某库视为采用。

首个场景为企业微信接收客户资料，调用既有知识 MCP，形成画像与需求讨论，再基于实际产品手册/案例证据详细生成售前方案和销售推进建议，支持销售修订。销售记录/跟进等后续业务及应用优化不扩充本轮选型验证范围。

## 2. 平台定案与候选比较

**定案：新 Agent 服务采用 Java / Spring Boot + Spring AI Alibaba Agent Framework / Graph 1.1.2.2。** Graph 管理研究、确认和方案节点，Agent Framework 承担节点内模型/工具循环，Spring AI 承担模型和 MCP 适配；不引入 Admin、Dify 或独立托管 Agent 平台。

固定依赖组合：Spring Boot 3.5.8、Spring AI 1.1.2、Spring AI Alibaba 1.1.2.2、Java MCP SDK 0.17.0。本地以 Corretto JDK 21.0.13 编译运行，Java 编译目标 17；部署 JDK 21，服务构建时锁定补丁版本。不能混用最新 Spring AI 2.x 或 Alibaba 2.0 预发布接口。现有 Python 3.12 知识服务及依赖保持不变。

用户已确认维护团队以 Java/Spring 为主。三者都通过了代表性本地验证，Java 候选同时满足团队维护能力与显式确认流程；因此选择它。没有依据把此次短流程的 tokens 或耗时当作性能排名。具体结果见[选型验证记录](验收记录/2026-10-26-Agent平台选型验证.md)。

| 候选 | 比较重点 | 项目边界 |
| --- | --- | --- |
| [AgentScope](https://github.com/agentscope-ai/agentscope) 2.x | 工具/MCP、状态与记忆、人工确认、服务运行和自定义 IM 适配能力；验证企业微信实际接入路径 | 不用内置 RAG 取代本项目单一知识 MCP；框架记忆不能替代业务事实与版本 |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | 状态流程、持久化/恢复、人工确认、模型/工具适配与应用服务组织；评估企微适配的自有工作量 | 已在历史依赖清单中不代表业务已调用；正式业务对象仍由领域服务管理 |
| [Spring AI Alibaba](https://github.com/alibaba/spring-ai-alibaba) Agent Framework / Graph | Java/Spring 团队维护适配、Spring AI 模型/MCP、Graph 持久状态与确认恢复；固定稳定 tag 验证，不能混用 2.x 预发布 API | Java Agent 服务经既有单知识 MCP 复用 Python 知识服务，不重建 RAG；企微仍需适配 |

Dify 和通用拖拽工作流编辑器不在当前架构范围。维护团队已确认以 Java/Spring 为主，Spring AI Alibaba Agent Framework/Graph 纳入同等验证；既有 Python 知识 MCP 保留，不要求迁移语言。首期只实现已选 Java Agent 服务，Python 候选保留为比较依据。

## 3. 同一代表性流程的兼容验证

| 维度 | 必须给出的证据或边界 |
| --- | --- |
| 企业微信入口 | 智能机器人接入方式、可信发送人、单聊/基础群 @ 路由、消息重试、任务状态和产物入口；真实租户可用能力另实测 |
| 现有知识 MCP | 能调用项目/产品检索与精确分节读取，保留来源、版本/hash、失败状态；遵循同版定向补读和按需图形规则 |
| 国产模型调用 | 所选 API/模型版本的工具调用、结构化结果、必要流式/超时及错误能用于该任务；密钥仅通过配置引用 |
| 任务与确认 | 同客户不同任务隔离，画像/需求/方案修订可追溯，人工补充后可继续，旧确认不覆盖新修订 |
| 持久化与恢复 | 重启/失败恢复后任务可继续，恢复重查权限和对象版本，外部写入和结果发送不重复 |
| 工程与维护 | Java/Spring 团队维护适配、Python 知识服务协议兼容、固定版本、领域服务边界、部署复杂度、许可与维护成本；明确需要自有适配的缺口 |

K24.1 完成比较和适配方案，K24.4 完成最小兼容验证并记录定案；它们是开发任务，不可仅以候选文档齐全标完成。需要真实企微/模型凭据的验证在获准配置下实施，模拟与真实结果分别注明。

选型产物至少包括一个确定的平台及版本、选择依据、代表性流程的实际结果、未验证/不支持范围，以及 K17 所需适配清单。验证失败应说明缺口是否阻塞首个场景，再依据证据定案，不能直接宣称兼容。

## 4. 最小公共底座与自有业务边界

K17 基于已定平台，仅建设可信身份和任务权限、企微接入、任务/状态/确认与恢复、现有知识证据适配、持久 worker/outbox、最小国产模型 API 调用以及产物保存。首期不先建设通用多岗位管理平台。

客户主体、来源、画像修订、需求基线、能力目录引用和方案修订属于本项目领域数据；正式商机、销售活动、跟进提醒、周报与跨任务销售知识管理后续扩展。框架状态与业务数据职责分开，公共项目知识仍按全生命周期采集，生成方案不自动回灌公共库。

公司模型代理、员工模型授权、配额用量、个人客户端模型准入和公司对话管理已作为独立项目移出，不计入候选比较、底座建设或售前闭环的前置。模型凭据也不授予知识、客户或仓库权限。

## 5. 与最后统一优化类别的关系

第一阶段验证来源与版本正确、工具可用、任务可恢复、详细方案可供销售使用；必要修复随原任务完成。K14 的专门检索基线与 RAG 调优、K25 的提示词/工作流/质量/时延/成本优化统一留到最后优化类别，不与本轮选型及开发并行，不作为平台定案的额外研究项目。

具体任务和状态仅维护于[产品迭代看板](产品迭代看板.md)，本文只定义选型与适配要求。

## 6. K17 必须补齐的实现

1. Spring Boot 应用 API 与企业微信适配：可信身份、消息去重、任务入口、确认和产物返回；租户长连接/单聊/群 @ 实测后确定细节。
2. 正式任务及修订模型、带版本的确认令牌、过期确认拒绝、权限重查、持久 worker/outbox；框架 checkpoint 与领域事务分别设计。
3. PostgreSQL checkpoint 方案及业务 schema。此次 FileSystemSaver 只用于本地顺序进程恢复；不得直接认作多 worker 生产方案。
4. 单知识 MCP Java 适配：工具白名单、结构化结果/错误归一化、精确 ID/revision/hash/section 引用和同版补读；生产 STDIO/HTTP 部署方式另按实际边界验证，K16 保持暂停。
5. 最小国产模型适配、限次/超时、失败分类及产物版本保存。Spring AI 1.1.2 原生 DeepSeek options 无显式 thinking 开关，此次使用供应商默认行为；若正式流程要求显式模式或 reasoning 往返，须实现适配并验证。
6. K15 将完整证据正文与引用身份作为独立结构保存，引用标识由服务渲染；不得仅传检索参数或让模型自由生成来源 ID。按真实手册完成详细方案、修订及销售人工验收。

以上实现状态只在看板维护。本次隔离探针不进入正式运行代码，不改现有 Python 锁文件。
