# 通用蒸馏规范

规范版本：distill-rules-v0.7（2026-10-20）。开始蒸馏任务时读取一次本任务规范和评分权重快照。

## 执行边界

1. 只读取本次任务已关联（attach）的材料。未关联的文件不读、不引用、不凭记忆补充。
2. 正文由你（客户端模型）生成；程序负责任务、材料引用、来源校验与草稿版本。生成的草稿是草稿，不是已审核知识。
3. 缺材料就声明缺口（gap），不虚构内容填补；缺少某类材料不等于项目不合格，但知识不得声称覆盖缺失内容。
4. 不确定的写"待确认"；未执行的步骤标"未完成"。
5. 蒸馏只支持标准 Word 文件 `.docx`、`.doc`。Excel、PPT、PDF、独立图片及其他格式仅保存在原件库，不得读取、转换、引用或交给本地模型蒸馏。
6. 若用户同时选择 Word 与非 Word，非 Word 文件被拒绝后立即停止并请用户确认是否只用 Word 继续；不得自行静默跳过。`.doc` 转换依赖 LibreOffice，转换失败就停止该材料处理。

## 事实状态与措辞纪律（v0.2）

1. 三分表达，逐条结论只能归入其一：
   - **已确认事实**：材料原文明确记载（标注来源位置）；
   - **未见证据**：本次材料中没有相关信息——材料的沉默不是否定；
   - **效力待确认**：有记录但未获正式确认（如未签字的变更、口头目标）。
2. 禁止从沉默生成否定事实：材料未提及签署状态，不得写"均未签署"；材料未记载生效，不得写"未生效"。正确写法是"材料中未见签署/生效记录，效力待确认"。
3. 选择依据与历史原因没有原始记录时写缺口，不得代拟理由；可以另列"模型建议"，逐条显式标注"模型建议，非项目事实，未经确认"，并与项目事实分开。
4. "唯一 / 必须 / 一定 / 不适用 / 保证 / 换取了"等排他、绝对或因果判断，必须有来源原文直接支撑；否则降级为待确认或模型建议。
5. "本文档由模型整体整理"不能替代逐条事实状态标注。

## 计数与统计纪律（v0.3，R02）

1. 表格计数逐行清点（用工具辅助，不目测），并写明口径：数据行、表头、空行、公式/图片行分别算不算。
2. 合计必须等于分项之和；摘要、正文、来源 supports 三处的同一数字必须一致。
3. 跨表数字不得直接相加或去重后当独立案例数；分母写清统计范围（如"H2:H74 共 73 行"要和表头位置核对）。

## 来源完备与读取覆盖（v0.3，R03/R04）

1. 正文出现的事实必须能追到本任务已登记来源；写"只使用本任务材料"时逐条自检，发现引用了未关联材料就补 attach+sources，或删掉该事实。
2. 关联其他知识一律用真实 knowledge_id+revision，不用会话内临时编号，不偷带未注册事实。
3. 每份材料在处理记录中标注三态：**已读文本未见 / 未查看附件 / 不可读**；未查看的附件不得推出"材料中不存在"。
4. 选图按知识主题与图类型覆盖，不凭文件名/大小抽样；关键流程图必须实际读图并保留可复原的节点与边；未看的图如实记"未核"，不预设为纯界面截图。

## 冲突判定纪律（v0.3，R05/R06）

1. 推断标注：原文理由与模型归纳逐句分离；"材料记载了 A"不等于可以推断 A 的代价、动机或唯一性——归纳单独标模型建议。
2. 判"冲突"前先对齐五要素：对象、范围、时间/阶段、单位口径、证据等级；区分**真矛盾、阶段演进、口径待核、范围包含、不同状态**（如"已验证"与"未上线"不互斥，70+ 与 73 是包含关系）。
3. 无法对齐的写"待核对"并列双方出处，不裁决谁正确。

## 流程复原纪律（v0.3，R07）

1. 流程图复原输出节点/边清单，每条边记录：起点、终点、方向、条件、动作。
2. 生成 Mermaid 后必须与原图**逐边回对**，不能只检查节点词是否齐全。
3. 箭头方向或起点含糊时标"待确认"，禁止凭业务常识换向或补线；原图孤立的节点保持孤立。
4. 图文两种表示必须一致；读图工具成功不等于边正确，回对通过才算完成。

## 事实状态标注

正文中的关键结论必须能区分以下状态，并在相应段落标注：

| 状态 | 含义 |
|---|---|
| 合同约定 | 来自合同/任务书的约定内容 |
| 设计目标 | 方案设计意图，未证实已实现 |
| 实际实施 | 有材料证明已实施的做法 |
| 验收确认 | 有验收材料确认的结果 |
| 人工经验 | 人员补充的经验判断（记录提供人） |
| 模型推断 | 你的推断，确认前不作为已验证事实 |

## 内容保留要求

- 蒸馏保留：场景、问题、约束、方法、步骤、选择原因、结果、适用条件、来源。
- 数值保留单位、口径、时间和出处；无依据的成效不得补造。
- 不为凑篇幅压缩必要步骤；也不把同一正文重复包装。
- 材料之间冲突时，并列记录各方说法与来源，不静默裁决选边。

## 核心正文范围（v0.6）

1. 生成知识前先读文档结构与正文文本，确定核心正文的开始位置；不要把目录之后立刻出现的说明页误当成核心内容。
2. 核心正文之前的封面、目录、使用对象/阅读说明、版本修订记录、术语/符号图例及其他编写说明均不进入蒸馏 MD，也不作为知识来源。
3. 上述范围中的图片、图例符号、孤立图形和表格一并排除；不要为它们调用 `distill_word_image`。先用图片资产的 `block_ref` 与 `block_context` 对照正文块确认范围，再请求核心正文中的图片。
4. 核心正文里的图片仍须逐张判断；流程图等业务图片按图像与流程纪律复原。只有确认属于正文前置说明或与知识无关的图片，才从复核范围排除。
5. 若正文起点或某图所属范围无法确定，标记待确认，不要仅根据图片外观或附近词语猜测。

## 来源绑定

- 每条重要结论在"来源映射"表中对应到：文件 ID、版本 ID、SHA-256、位置（章节/页码/表号/图号，整篇支持可写"全文"）、支持范围。
- 位置尽量定位到章节或页码；"全文"仅用于贯穿性结论。
- 人工补充不是原件内容：单独记录提供人与时间，在正文中标注"人工补充"。
- 来源必须来自任务已关联材料的已关联版本；提交时程序会校验。

## 图像与流程

- 图像结果至少包含：内容描述、来源文件与版本、页/图/幻灯片位置、不确定项。
- 流程图保留节点、角色、顺序、分支条件、异常路径；区分忠实复原与整理建议。
- 不能凭空间接近推断连接；无法确认的标记"待核对"。
- 原图以文件 ID+版本引用；本轮不在 md 中嵌入图片资产，需要时在"图像与流程资产"章节写明定位。

## Word 阅读与质量评分（v0.7）

1. 每份已关联 DOC/DOCX 调用 `distill_word_content` 读取到 `has_more=false`。默认较大分页以减少工具往返；首批内容同时返回结构摘要、图片位置与上下文。上传原件阶段仍只保存，不运行解析。
2. 先确定核心正文起点，再跳过封面、目录、对象说明、版本记录、正文前说明、图例、页眉页脚和无关装饰。只对核心正文相关图片调用 `distill_word_image`；图片理解由客户端多模态模型完成，不用 OCR。流程图内容不清时记录待确认，不猜测。
3. `draft_submit.quality_report` 提供 `scores`（模型负责的维度 0–5 分）、`evidence`、`flags` 和 `unresolved_items`。评分权重来自 `评分权重.json`，由业务人员维护并在任务启动时固化版本与哈希。MCP 自动计算来源追溯和章节结构分。
4. 缺少章节、表格/图片覆盖不完整、来源定位粗、流程图未复原，均作为评分扣分和待核实项记录，不阻止草稿提交，也不要求为提高分数反复提交。服务端可确定的文件版本、哈希和结构信息不要求模型重复抄报。
5. 仅文件损坏/哈希不一致、错误版本、非 Word 材料和没有可读正文属于硬阻断。低分草稿仍导出为 `draft`，质量分用于未来检索排序参考；不代表事实正确、人工审核通过或已发布入库。

## 输出格式

正文按 templates/项目知识模板.md 组织（UTF-8 Markdown）。建议保留来源映射、冲突缺口与待确认项、处理记录；缺项记录评分与待核实项，不阻止草稿提交。来源由服务端按已关联材料补全或使用客户端给出的具体位置。
