适用对象：接手 Knowledge Distillation 开源代码的下游开发人员

## 交付包与当前状态

代码压缩包：`knowledge-distillation.zip`。公开仓库：[Mikajin1206/knowledge-distillation](https://github.com/Mikajin1206/knowledge-distillation)，当前基线提交 `13a783658ae771a65c5b13ccb3be843af833057b`。仓库同时提供英文和中文版 README，采用 MIT License。

当前实现包含本地原件存储、项目与文件管理、Word 蒸馏、评分、MD 与 JSON sidecar 导出，以及 stdio MCP 和 `knowledge-distillation` Skill。**本地文件存储适配器不等于公司文件服务器接入；草稿导出不等于审核通过、RAG 发布或正式检索可用。**代码尚未实现生产级公司文件服务适配、审核发布状态机和 RAG 发布集成。

在原开发环境中，Python 自动化测试 70 项通过；为遵守发布范围，测试目录和过程文档没有放进此代码包，因此下游无法仅靠 ZIP 重现这 70 项结果。请把它视为原开发环境的测试记录，不要据此宣称当前代码已通过下游环境或生产验收。

WorkBuddy 5.8.3 已加载优化版 Skill，并通过 MCP 1.1.0 完成一轮 Word 蒸馏主流程、评分、单次首稿、MD/sidecar 导出、哈希检查和任务清理；Excel 原件只保存，未读取或蒸馏。该完整流程之后，章节别名诊断修复有自动化覆盖，EMF 中文渲染修复通过 WorkBuddy 图像通路验证；尚需一个最小新任务确认两项最终修复共同反映在导出产物中；新草稿还应验证章节路由标识完整且 sidecar 路由清单有效。自动化测试、单独图像通路和哈希匹配不能替代这项窄范围回归。

## 不可改变的业务原则

1. **按项目全生命周期收集知识。** 阶段包括立项与范围、调研与需求、方案与设计、实施与变更、测试与验收、运维与改进。采集标准不能被售前问题牵引；售前所需信息由售前 Agent 从通用项目知识中抽取。实施和运维也要能消费同一知识层。
2. **原件与知识分开。** 上传原件只保存、登记元数据和版本，不自动解析、不调用模型、不蒸馏、不索引。原件身份要稳定，至少能追踪项目、文件 ID、版本 ID、SHA-256、文件名及上传记录。读取指定版本时重新核验哈希；蒸馏临时副本关闭任务后清理，原件不能被覆盖或删除。
3. **蒸馏严格限于 Word。** 仅 `.docx` 和 `.doc` 可作为蒸馏材料。Excel、PPT、PDF、独立图片等可以作为原件保存，但不得解析、交给模型或绕过限制用于蒸馏。混合选择时必须先明确拒绝非 Word，并询问用户是否只用 Word 继续，不能静默忽略。旧版 `.doc` 转换失败时应停止该材料并保留原件。
4. **只蒸馏核心内容。** 封面、目录、适用对象说明、图例、版本修订说明及其中孤立图形，以及页眉、页脚和无关装饰不进入知识正文。无关图片在确认后排除，不触发额外视觉处理，也不占用质检资源。
5. **图片由客户端多模态模型理解。** 不使用 OCR 代替视觉识别，不声称服务端执行了视觉推理。只对核心正文相关图片调用图像能力。PNG/JPEG/GIF/WebP 可直接传递；SVG/EMF/WMF/BMP/TIFF 依赖 LibreOffice 转为 MCP 可读 PNG。转换失败或文字不清时标记待确认，不猜测图中文字。
6. **流程图要保留结构和不确定性。** 描述流程时保留节点、起点终点、方向、条件、角色、动作和异常路径；逐条对照原图核验连接关系。不能根据图形距离猜连线，不能把流程图摘要当作逐边复原通过。看不清的边、节点或方向明确列为待确认。
7. **事实、人工补充和推断必须分开。** 每个业务事实应关联已登记的材料版本和具体位置；无证据只能写“材料未提供／未发现证据”，不得改写成“事实不存在”。模型归纳、人工补充、材料陈述、独立验证和待确认事项必须明确区分。冲突先对齐对象、范围、时间阶段、单位和证据等级，不静默裁决阶段演进或范围差异。
8. **质量评分是排序信号，不是反复试错门槛。** 评分权重由业务人员维护，合计为 100；任务启动时固定规则版本和哈希。低分、图片不确定或部分章节缺项应形成评分与缺口说明，正常生成草稿。文件类型、版本、哈希、来源身份等完整性错误仍是硬阻断。评分不代表项目经理审核或发布许可。
9. **效率要体现在工作流里。** 每个任务读取一次指引；正文按分页读完，不重复解析同一材料；确定正文范围并排除无关图片后，调用一次质量报告模板；按完整结构一次提交首稿；导出返回哈希已匹配时，不重复做同一校验；任务结束关闭并清理临时副本。只针对服务端明确指出的契约错误做有针对性的修复，不为追求高分而重复提交同一知识。
10. **生成结果不自动回灌。** Agent 的售前答复、实施方案和运维答复都是应用输出，不是新的已确认知识。需要纳入通用知识时必须重新执行来源登记、审核和发布。

## 后续开发顺序与验收标准

### 1. 最新修复的 WorkBuddy 最小回归

完整主流程已验收；下一次只需在目标 WorkBuddy 使用当前 MCP 和 Skill 创建一个隔离任务，覆盖最新章节别名诊断和 EMF 字体修复后的导出。不需要重跑历史项目的全部材料。建议使用已授权的脱敏 Word 和一份非 Word 文件验证拒绝及混合选择确认，不要把客户原件放进公开仓库。

通过条件：

- 用户不需要记住 MCP 工具名、内部 ID 或哈希；Skill 能逐步说明当前动作并避免重复提问。
- 只处理用户明确选择的完整路径；不枚举父目录，不扫描其他本地材料，不使用其他 MCP、shell、Office 工具或本机读取绕过 MCP 工作流。
- 非 Word 原件可以登记，但蒸馏时由服务端拒绝；混合材料会先停下并确认，不会静默继续。
- 任务按阶段创建，文件版本固定，正文分页读取完整；核心正文范围筛选后，才请求相关图片；客户端模型对不确定处标记待确认，不得臆造细节。
- 评分、质量报告和来源信息在首稿一并提交；单份知识只提交一次首稿。导出时哈希匹配，任务关闭后临时副本清理，原件仍可按原 ID/版本查回。
- 全过程记录实际 MCP 工具调用、错误、重试和导出结果；明确区分自动化测试、真实客户端操作、人工内容复核三类证据。

### 2. 公司文件服务器适配

开始编码前，先取得并核对现有公司文件服务/MCP 的真实接口、权限和错误行为。不要再造一套公司文件服务器，也不要把当前本地存储误标成生产接入。

需确认并形成接口映射：上传会话或客户端传输方式、项目关联、稳定 file ID、版本 ID、SHA-256、重复内容策略、标签和阶段、指定版本读取、权限校验、过期链接刷新、资产回取、临时副本和清理、幂等键、限流及失败重试。大文件不能无条件通过 MCP 参数整体 Base64 传输。

通过条件：

- 在隔离测试项目上传两份文件；重复上传不会丢失项目、文件名、版本和上传记录关系；内容变化生成独立版本。
- 能按项目/标签查找，并读取指定版本；读取后 SHA-256 与服务端记录一致，错误或过期引用可以明确恢复或安全失败。
- 上传不会触发解析、模型调用、知识生成或 RAG 写入。
- 删除/清理任务工作副本不会删除公司文件服务器原件；跨项目、权限不足、哈希不一致等失败路径都有明确结果和审计记录。
- 以真实服务器的隔离环境结果验收。仅有 mock、模拟接口、CLI 单测或静态代码不能算公司服务接入通过。

### 3. 项目经理审核与版本发布门

审核必须绑定不可变的 `knowledge_id + revision + content_hash` 及来源/资产清单哈希，记录审核人、时间、结论和意见。正文、来源、重要适用条件发生变更时生成新修订并重新审核。身份与权限由服务端校验，不能信任客户端自报“已审核”。

通过条件：

- 草稿、审核中、退回、批准、发布中、已发布、发布失败、已撤回/被替代等状态有可查询的状态转换和操作日志。
- 未审核草稿、被退回版本、审核后内容已变版本均无法发布到正式 RAG。
- 审核人和项目权限经过真实身份授权检查；重复审核或重复发布按幂等契约处理。
- 发布失败可以重试；新版本完整发布前旧的有效版本仍可用，不出现半套新旧内容混杂。
- 撤回或被替代版本退出默认检索，但仍保留审计和来源追溯能力。

### 4. RAG 入库、切片与回读

先向公司侧确认入库触发方式、投递目录/API、sidecar 字段映射、状态过滤和版本切换接口，再实现适配。RAG 只接收已审核知识；正式检索默认不得返回 `draft`、被撤回或已替代的版本。

以下切片标准属于验收要求：

- frontmatter 解析为文档元数据，不进入索引正文。
- 来源映射表和处理记录由 sidecar/元数据承载，不进入索引正文。
- 每个 `##` 至 `######` 标题必须带唯一 `kd-section` 标识，并标注 `rag=body|metadata|audit|exclude`。只按标识路由，不根据标题语义猜测；缺失、非法或重复标识时路由校验失败且不生成检索正文。
- 仅 `body` 章节进入语义切片；`metadata` 进入结构化字段；`audit` 仅留审计；`exclude` 不进入正文或检索元数据。章节标题路径和 section ID 进入 chunk 元数据。
- 每个 chunk 都保留可回链的 `knowledge_id`、revision、项目/阶段和来源文件版本及位置。
- 事实状态、适用边界、冲突、缺口和待确认内容保留在索引正文中，不能当作噪音删除。
- 入库前后核对内容哈希。哈希只证明内容没有变化，不证明事实正确。
- 若现有 RAG 不能满足上述切片标准，需开发清洁视图投递：审计版归档，清洁版用于索引，不能把原始审计版整篇直接塞入正式检索。

通过条件：

- 用同一知识样本检查入库前 Markdown、sidecar、切片清单、索引元数据和读回结果，逐项一致。
- 能证明 frontmatter/来源表/处理记录未进入索引正文，事实状态和适用边界仍在。
- 模拟重复投递、超时、部分失败、版本替换和撤回；幂等、回滚和旧版本可用性符合契约。
- 验证来源引用能打开正确的原件版本或稳定资产引用；链接过期时按契约刷新，不伪造来源。

### 5. 售前、实施、运维 Agent

三类 Agent 从同一套项目全生命周期知识中按任务抽取，不改变原始采集范围。售前 Agent 负责需求到能力、方案和案例证据的组织；实施 Agent 侧重可执行步骤、配置、依赖、变更和验收；运维 Agent 侧重环境/版本、现象、诊断、根因、处置、验证和改进。

每个 Agent 交付前必须通过：

- **引用纪律：**每条业务事实可回链到知识版本及来源位置；无证据时明确说无证据，不用低相关结果凑答案。
- **事实状态继承：**保留约定、目标、已实施、已验证、经验、推断等状态；冲突和待确认事项不被静默裁决。
- **输出可用：**面向人的结果结论先行、结构清楚、步骤完整；哈希、解析记录、规则版本等内部信息不污染正文，来源以适当引用呈现。
- **不回灌：**生成的答复或方案不会自动进入通用知识库。
- **固定问题集实测：**覆盖命中、无关结果、引用正确性、版本适用性、无证据时的拒答；记录 top-k、错误和人工复核，不把“能运行”作为质量结论。
- **真实材料首稿：**在没有人工提示补答案的首稿上验证规范，保留失败样例和修正证据；报告未验证项，不把模型自评当事实核验。

## 每个工作包的交付证据

开发每个阶段都应交付以下材料，短小但可复核：

- 本阶段范围、接口依赖和未解决假设。
- 实际改动清单、数据迁移/回滚方法及配置说明。
- 相关自动化检查结果及环境/版本；只报告本次实际运行的结果。
- 真实客户端或隔离服务端操作记录；没有真实接口时清楚标注“模拟/未验证”。
- 关键失败路径、哈希、版本、来源和清理结果。
- 本阶段结论：通过、部分通过或未通过；明确哪些仍需人工审核或外部系统确认。

## 发布与资料安全

- 不把客户原件、真实项目名称、数据库、蒸馏产物、访问令牌或个人路径放入代码仓库、公开压缩包、截图或测试夹具。
- 不将 `.env`、真实 MCP 客户端配置、签名私钥或访问凭据提交版本库。
- 公开项目当前未附测试目录。当前开发源的路由改造后自动化测试共 70 项通过；下游开发仍应在自己的环境建立针对改动的必要回归覆盖，不要用该结果替代本次验证。若需复现，应在获准的开发仓库中维护测试和运行说明。
- 不因引入解析器、Office 工具或新 MCP 工具而无边界扩张。先确认现有能力是否可复用；相似用途合并为少量清晰工作流工具，工具描述应让模型知道何时调用、调用顺序、输入输出及失败后的处理方式。
- 任何正式 RAG 写入、发布、权限或数据迁移验收，都必须在明确的隔离环境中完成，报告清楚标出实际写入范围和回滚证据。

## 本轮明确不应误报为已完成

公司文件服务器真实接入、项目经理审核门、正式 RAG 发布和检索质量提升、生产级多人权限、售前/实施/运维 Agent 真实业务验收，均不包含在当前代码包的完成状态中。它们必须分别按上述标准完成并提供对应证据，不能由单元测试、README 描述、MCP 工具清单或一次哈希通过推定完成。
