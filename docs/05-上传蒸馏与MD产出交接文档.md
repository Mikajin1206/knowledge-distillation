# 当前代码契约与后续接续标准

更新日期：2026-10-22。本文为当前代码与未来系统接续的权威契约。旧版本操作记录、历史测试结论和原始过程材料见 `docs/archive/`，不得将历史 MCP 版本描述当成当前接口。

## 1. 当前交付边界

1.2.1 已通过 WorkBuddy 验收，为 **单 MCP、30 工具**；1.3.0 在同一服务提供 **31 工具**，WorkBuddy 已验证 OA 产品/领域元数据正向入库与 RAG 正反筛选。项目完整自动化套件 138 项通过。原有 21 个蒸馏工具加 9 个本地知识生命周期工具。已交付六阶段蒸馏、Word 结构读取与图片传递、Markdown + JSON sidecar、正文哈希、本机审核记录、异步发布任务、逐块读回校验，以及图形 JSON 在 `local_versioned_store` 中的独立版本上传和读取。章节路由仅支持 `body`/`exclude`；生命周期 `stage` 由已审核 sidecar 的路由集合与 metadata 提供，不进入 MD 最小头；`knowledge_type` 仅为补充文档类型属性。来源、评分和处理证据由 sidecar/服务记录承载。撤回与部分负向场景仍未做 WorkBuddy 黑盒验证。

当前开发身份范围为 `local_development`，由 `CKP_LOCAL_ACTOR` 和 `CKP_REVIEWER_IDS` 配置。真实公司文件服务器适配、remote auth、生产发布、生产多用户权限和备份、售前/实施/运维 Agent 尚未实现。不得将本地 adapter 或沙箱发布描述为公司服务已接通。

`draft_export` 在本地文件适配下返回显式导出路径，这是现有交付契约；未来服务器模式应迁移为经过授权的下载链接。路径脱敏要求针对错误和 RAG 输出中的内部路径，不得误称当前导出路径契约不存在。

## 1.1 MCP 服务统一原则（2026-10-22）

WorkBuddy 客户端只配置并连接一个 MCP server：`knowledge-distillation` / `ckp-mcp.sh`，当前共 30 个工具。原件、蒸馏、审核、发布、RAG 入库、检索、读取和撤回作为该 server 下的多个工具提供；服务端内部仍按职责拆分模块、存储适配器和授权检查。历史 `rag-mcp.sh`、`ai-generate-solution-mcp.sh` 及双/三 server 配置仅用于历史专项开发或独立测试，不作为 WorkBuddy 的额外服务配置。 旧 `knowledge-rag-development`、`ai-generate-solution` 模块仅作内部开发兼容保留，不单独对外注册；方案生成独立入口停用，客户端可基于主 MCP 知识工具结果完成后续生成。

## 2. 当前材料与交互契约

- 上传可以保存各种文件，只登记原件和元数据，不解析、不蒸馏、不调用模型、不索引。
- 上传与蒸馏是两种独立意图，必须在对话中区分：用户只说上传/提交/归档时仅归档，完成后再提示可另行指定关键 Word 蒸馏；用户明确要求蒸馏时，仅处理其明确指定的文件。“全部蒸馏”视为明确指定整批；只说“关键文档”但未指出文件时，追问一次范围。只说“处理/整理”等意图不明时，先询问仅归档还是同时蒸馏及文件范围，答复前不上传、不蒸馏。不得从文件名、格式、内容或选中文件推断蒸馏意图/关键文档。若用户已明确要求上传并蒸馏且给出范围，不重复确认，先归档再继续蒸馏。
- 蒸馏产物分组规则：默认每份 Word 独立蒸馏并产出一份 MD；用户明确说“全部蒸馏”时也按文件逐份产出。多份 Word 请求蒸馏时，提醒项目经理 MCP 支持将明确指定的一组资料合并分析并共同形成一份知识文件；没有明确合并指令时直接按默认逐份执行。只有项目经理明确要求合并时，才将这些 Word 关联到同一任务并产出一份综合 MD。未明确提出合并，不得自动按项目、阶段、主题或内容相似度合并。合并产物必须保留各来源 file_id/version_id/hash 与位置，冲突并列标记并待确认。验收记录和最终报告须列出源文件到蒸馏任务及 MD 的完整映射。
- 上传项目名称必须由项目经理提供；使用现有 `project_list` 查看候选。相同/相近名称由项目经理判断，同一项目沿用清单名称并再次确认；模型不得猜名、自动合并或改写归属。此流程复用现有项目清单，不新增项目名称查询接口。
- 蒸馏只接受 `.doc` / `.docx`。非 Word 请求由服务端拒绝；混合材料必须暂停并向用户确认是否只用 Word 继续，禁止静默跳过或借其他工具读取。
- 原件以项目、file_id、version_id、sha256 和上传关系标识。蒸馏任务关联具体版本；读取时重验哈希；原件在任务结束后仍可取回。
- 按六个生命周期阶段组织材料，不按售前问题反向决定收集范围。缺口要登记；人工补充注明提供人；规范和评分权重在任务启动时固化快照。
- 每任务读一次 guidance；正文分页读到终点；先确定核心正文范围，再筛选图片；调用一次质量报告模板；提交一份完整首稿；导出返回哈希后关闭任务清理工作副本。
- 质量分是未来排序/提示信号，不是审核。低分不阻止草稿；类型、文件版本、哈希、来源归属等完整性错误仍拒绝。
- 职责边界：MCP 负责用户指定材料的归档、解析/渲染、忠实蒸馏及技术来源追溯。项目经理负责材料规范和业务内容确认。MCP 不审查签署/盖章、文件标识/版本/日期一致性、附件或测试验收材料齐套、方案决策闭环、编码/业务口径一致性、图像姓名与人员档案，也不对这些事项生成缺陷、缺口或待确认项。蒸馏只忠实保留实际读取到的陈述，不判断材料正确性、合规性或业务方案完整性；用户要求上述审查时，说明不属于 MCP 蒸馏范围。

## 3. 内容、图片和来源要求

正文应保留业务场景、问题、约束、解决方法、步骤、结果、适用条件和用户指定的待处理事项。将材料陈述、人工补充和模型归纳分开；缺少蒸馏所需信息时不得补造。MCP 不盘点未关联附件或验收材料，不做材料规范、齐套、业务正确性、方案完整性或内部一致性审查。明确授权多文件合并时，若来源陈述差异直接影响合并语义，保留出处与原陈述，不自行裁决。

只处理核心正文里承载业务信息的图片。封面、目录、使用对象说明、版本记录、图例、页眉页脚和无关装饰图片排除，不请求模型复核，不进入正文。客户端多模态模型直接视觉识别；服务端不运行 OCR 或视觉推理。PNG/JPEG/GIF/WebP 可直接经 MCP 传递；SVG/EMF/WMF/BMP/TIFF 由 LibreOffice 转 PNG。转换器生成无效或全透明/单色 PNG 时，MCP 必须拒绝图像并说明原因，客户端将其记录为未识别/待确认；不可将空白图当作成功，也不可推测流程节点。能力预检返回服务、解析器和渲染器版本；WorkBuddy 真实验收须先记录这些版本。渲染成功不等于图文可读；不清楚时保留待确认。

可复原流程图、系统结构图作为受保护图形资料保存。当前蒸馏和导出阶段将完整结构暂存在 JSON sidecar 的 `quality_report.flowcharts[]`，包含 `asset_id`/`asset_type`、原件 file_id/version_id/hash/位置、节点、边/关系、方向、条件、动作、分组/泳道/布局（原图可识别时）及待确认项。本地发布会将每张图作为独立 JSON 文件写入 `local_versioned_store`，记录精确 file_id/version_id/SHA-256 并逐版本读回；图形 JSON 不上传到向量库、不参加普通文本切片。Sidecar 顶层 `protected_assets` manifest 记录 `asset_id`、版本映射、哈希和来源定位；Markdown 正文及分节清单只保留用途说明和 `asset_id` 引用。检索命中后，若回答需要图形细节，按 asset_id 读取指定知识修订对应的图形版本并核验哈希，返回完整 JSON，不静默截断。此本地适配行为不代表公司文件服务器已接通；服务器迁移需使用其授权的版本读取机制。每条边对照原图核验；孤立节点、并行、回环、分支和终止状态不能省略。Mermaid 只作可选展示，不能替代结构数据；未确认部分保留并标待核，不声称完整复原。

来源应绑定任务内材料、file_id、version_id、sha256、可定位位置及支持范围。MD 的 `content_hash` 证明正文字节一致，JSON sidecar 的 `sidecar_sha256` 独立校验规范化 sidecar 内容；`draft_verify(md_path, sidecar_path)` 还核对两者的知识修订身份。两项哈希用于发现单文件变化，不证明事实正确，也不能代替对抗性场景下的签名或可信交付包校验。

每个 `##` 至 `######` 业务章节标题末尾必须包含 `<!-- kd-section id=<稳定英文标识> rag=<body|exclude> -->`。`body` 章节进入语义检索文本；`exclude` 不进入检索文本。新版路由不包含 `metadata` 或 `audit`：业务事实无论标题层级或呈现形式都在正文；详细来源、材料读取覆盖、处理记录、模型/规范信息、评分证据和审核发布引用由 `sources`、`quality_report` 与 JSON sidecar/服务记录承载。`src/ckp/md_render.py` 的 `extract_rag_payload()` 只读取标识，不根据标题语义猜分类；它按章节层级提供 heading_path，便于切片附带父级上下文。每个分节清单应带 `document_ref`（knowledge_id、revision、content_hash）、来源版本集合 `source_refs` 和正文实际引用的 `protected_asset_refs`；这些是身份/回链信息，不把全文复制进分节。缺失、非法、旧版或重复标识时 `routing_valid=false` 且检索正文为空；草稿仍可保存。旧版 `metadata`/`audit` 标记不自动转换或索引；使用原件重蒸馏，或人工逐节复核后生成新修订。sidecar 的 `rag_selection` 是路由校验清单，不代表已审核或获准发布。当前本地 `read_knowledge` 支持指定版本读取分节目录、按 section ID 补读和经授权的完整正文读取；默认不返回完整 sidecar。图形 JSON 不随普通 RAG 结果返回，只有用户需要图形细节时才按精确知识版本与 asset_id 调用 `get_asset`，服务端校验映射和 SHA-256 后返回完整结构。

## 4. 公司文件服务后续适配

真实公司文件服务及 remote auth 当前尚未接通。开始适配前核查公司现有文件服务/MCP接口、权限和隔离环境。对接必须映射上传会话、项目关系、文件/版本身份、哈希、重复上传、指定版本读取、授权下载链接刷新、资产回取、幂等、错误/重试、临时副本和清理。受保护图形 JSON 作为独立文件上传文件服务器，以 `asset_id` 关联并保留服务端 `file_id/version_id/sha256`；检索得到 `asset_id` 后按这个身份回取精确版本。若文件服务不支持 asset_id 直查，发布清单需保存映射，不能靠文件名模糊匹配或本机路径。不要新建平行文件服务，不要默认把大文件整体 Base64 塞进 MCP。

验收至少包括：隔离项目上传两种文件；重复上传关系保留；内容变化形成新版本；项目/标签查找；指定版本读回且 SHA 相符；权限拒绝、链接过期、网络失败可明确处理；原件不被任务清理；上传不触发解析或 RAG。Mock 和本地 SQLite 测试只能证明适配器行为，不能证明公司服务已接通。

## 5. 审核与 RAG 接续标准

当前本地服务已实现审核记录和异步发布状态机：审核绑定 `knowledge_id + revision + content_hash` 及 sidecar 快照，发布任务逐块写入并逐块读回；完整校验通过后才切换当前活动版本。审核身份与角色由服务端环境配置绑定，范围 `local_development`，不是 production identity。以下公司侧要求仍是生产接续标准，不代表已经对接公司服务。

审核应由项目经理或有权限的人员执行，绑定 `knowledge_id + revision + content_hash` 及来源/资产清单哈希、审核身份、时间和结论。正文、来源或关键适用条件变更时生成新修订并重新审核。服务器端核验权限；未审核或审核后变更的版本不得进入正式 RAG。

RAG 入库遵守以下规则：

| 标准 | 验收要求 |
|---|---|
| 文档元数据 | frontmatter 解析为文档级元数据，不进入索引正文 |
| 去除纯审计噪音 | 来源映射明细、处理记录由 sidecar/元数据承载，不进入知识正文或检索文本 |
| 章节切片 | 仅切片 `rag=body` 章节，不跨标记章节；标题路径和 section_id 进入 chunk 元数据。`exclude` 不得进入向量正文 |
| 来源可回链 | 每个 chunk 关联 knowledge_id、revision、项目/阶段、source 文件版本和位置 |
| 受保护图形 | chunk 只带 asset_id/资产引用；图形 JSON 单独保存在文件服务器，按需取指定版本，不进入 RAG 正文或向量切片 |
| 保留防幻觉信号 | 事实状态、适用边界、冲突、缺口和待确认项保留在正文 |
| 状态过滤 | 正式检索默认只返回已审核、已发布、当前有效版本；draft/撤回/替代版本不默认命中 |
| 哈希与版本 | 入库前后检查哈希；新版本成功切换前旧版本持续可用 |
| 清洁视图 | 若现有 RAG 无法按以上规则切片，先生成审计版与清洁投递版，不整篇灌入审计版 |

发布重复调用必须幂等；部分失败不能暴露半套新版本；失败可重试并有日志；撤回后从默认检索退出但保留审计。验收要检查源 MD、sidecar、切片、索引元数据和读回内容，不以“索引条数增加”作为质量结论。

## 6. 售前、实施、运维 Agent 验收

三类 Agent 从通用生命周期知识层按任务抽取，不修改知识采集标准。每个业务事实要有知识版本与来源定位；无证据时明确说明；继承来源事实状态、版本范围、冲突和不确定性。面向人的输出清楚可用，内部哈希、处理日志和规则版本不泄漏到答案正文；Agent 输出不得自动回灌。

上线前用固定问题集覆盖命中、误命中、来源引用、版本适用性、无证据拒答及边界条件。记录 top-k、来源、答案事实核验、人工复核、处理时间。阈值在代表性试点数据上制定；不得仅以“能运行”或模型自评分宣称验收通过。
