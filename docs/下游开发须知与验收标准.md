## 不可改变的业务原则

1. **按项目全生命周期收集知识。** 阶段包括立项与范围、调研与需求、方案与设计、实施与变更、测试与验收、运维与改进。采集标准不能被售前问题牵引；售前所需信息由售前 Agent 从通用项目知识中抽取。实施、运维和开发也要能消费同一知识层。
2. **原件与知识分开。** 上传原件只保存、登记元数据和版本，不自动解析、不调用模型、不蒸馏、不索引。原件身份要稳定，至少能追踪项目、文件 ID、版本 ID、SHA-256、文件名及上传记录。读取指定版本时重新核验哈希；蒸馏临时副本关闭任务后清理，原件不能被覆盖或删除。
3. **蒸馏严格限于 Word。** 仅 `.docx` 和 `.doc` 可作为蒸馏材料。Excel、PPT、PDF、独立图片等可以作为原件保存，但不得解析、交给模型或绕过限制用于蒸馏。混合选择时必须先明确拒绝非 Word，并询问用户是否只用 Word 继续，不能静默忽略。旧版 `.doc` 转换失败时应停止该材料并保留原件。
4. **只蒸馏核心内容。** 封面、目录、适用对象说明、图例、版本修订说明及其中孤立图形，以及页眉、页脚和无关装饰不进入知识正文。无关图片在确认后排除，不触发额外视觉处理，也不占用质检资源。
5. **图片由客户端多模态模型理解。** 不使用 OCR 代替视觉识别，不声称服务端执行了视觉推理。只对核心正文相关图片调用图像能力。PNG/JPEG/GIF/WebP 可直接传递；SVG/EMF/WMF/BMP/TIFF 依赖 LibreOffice 转为 MCP 可读 PNG。转换失败或文字不清时标记待确认，不猜测图中文字。
6. **流程图要保留结构和不确定性。** 描述流程时保留节点、起点终点、方向、条件、角色、动作和异常路径；逐条对照原图核验连接关系。不能根据图形距离猜连线，不能把流程图摘要当作逐边复原通过。看不清的边、节点或方向明确列为待确认。
7. **事实、人工补充和推断必须分开。** 每个业务事实应关联已登记的材料版本和具体位置；无证据只能写“材料未提供／未发现证据”，不得改写成“事实不存在”。模型归纳、人工补充、材料陈述、独立验证和待确认事项必须明确区分。冲突先对齐对象、范围、时间阶段、单位和证据等级，不静默裁决阶段演进或范围差异。
8. **质量评分是排序信号，不是反复试错门槛。** 评分权重由业务人员维护，合计为 100；任务启动时固定规则版本和哈希。低分、图片不确定或部分章节缺项应形成评分与缺口说明，正常生成草稿。文件类型、版本、哈希、来源身份等完整性错误仍是硬阻断。评分不代表项目经理审核或发布许可。
9. **效率要体现在工作流里。** 每个任务读取一次指引；正文按分页读完，不重复解析同一材料；确定正文范围并排除无关图片后，调用一次质量报告模板；按完整结构一次提交首稿；导出返回哈希已匹配时，不重复做同一校验；任务结束关闭并清理临时副本。只针对服务端明确指出的契约错误做有针对性的修复，不为追求高分而重复提交同一知识。
10. **生成结果不自动回灌。** Agent 的售前答复、实施方案、运维答复和开发建议都是应用输出，不是新的已确认知识。需要纳入通用知识时必须重新执行来源登记、审核和发布。

知识蒸馏中的图片理解与产品手册图片回取是不同契约：后者只按精确版本和图号/位置回原图，不做图片语义解析。Agent材料接收和产品手册范围扩展均需独立定义，不绕过现有入口限制。

## 后续开发与验收接续

### 1. 现有知识能力维护（K01–K11）

修改前读取05与相关代码，保留原件、版本、上传记录、MD/sidecar哈希和章节身份。针对实际改动核对上传隔离、材料范围、目录产品/领域、来源、草稿/审核/发布独立状态及分节读取；不因新Agent需求改写既有工作流。

发布重复调用幂等，部分失败不暴露半个版本，逐块写入并读回后激活。撤回阻止默认命中和受限读取但保留历史。产品资料与项目库分域，手册图像从指定哈希原件回取且不另存副本。

### 2. Agent最小基座与售前试点（K17/K15/K14）

K24 已完成本地最小选型验证，2026-10-26 修订确定 Python LangGraph（现有代码全部为 Python，原 Java 定案作废），保留 Python 单知识 MCP；后续按 K17 建设渠道无关的可信身份、最小任务上下文、状态/确认、现有知识适配、最小国产模型 API 调用及产物保存。首期贯通 S1 搜知识、S3 客户画像、S4 需求讨论和 S5 售前方案，按 K15.10 完整客户场景验收；不等待 PDF 或培训资料；K14.1 专门优化基线及其他应用调优统一归最后优化类别，首期仅保留来源、版本与业务可用性等必要验收。企微租户接入由 K17.5 在所有 Agent 的最后统一完成，K15.9 届时验收真实客户端，当前不做；飞书不在首期。销售记录、商机阶段、跟进、提醒、周报及跨任务销售知识管理后置，不作为首期前置。输入输出、确认、权限及失败规则遵循 03。

销售业务事实以结构化记录为准，需求基线、画像和报告绑定修订。网页和行业案例只是来源或假设，不能单独证明客户需要。周报从确认活动汇总，不用请求数代替沟通次数。销售独立库需新建销售域分类与授权，不伪造六阶段或自动回灌公共库。

售前方案按 03 的八部分结构及 7.1–7.6 实现：逐需求检索并按需补读产品手册/项目证据，正文展开业务步骤、规则/异常、系统衔接、能力分类、实施条件和价值机制，保留来源与设计建议的区别。内部证据包不能替代正文细节；只列模块名称或概括性价值不能通过首期方案验收。下一轮客户沟通的目的、对象角色、问题、材料与期望确认结果属于方案输出，持续跟进台账和提醒仍后置。

### 3. 公司知识生产环境（K16，暂停）

本次不恢复。未来明确恢复后先取得真实文件服务、身份和错误契约，再做源文件/资产上传、指定版本读取、SHA-256、授权刷新、幂等、审核/发布和撤回同步。远程客户端不可依赖服务端访问员工本机路径；传输采用获准上传会话或文件服务能力。

图形JSON精确映射资产到公司file/version/hash，读回失败阻止依赖版本激活。审核角色由服务端与项目责任关系核验，修改内容重新审核；不能复用本机actor作为生产身份。迁移与恢复覆盖元数据、原件、资产、审核、索引和活动指针，不只复制向量。

### 4. 实施、运维、开发Agent（K18–K20）

先交付只读问答/分析和有来源的建议，按岗位验证项目/环境/产品/代码版本、事实状态和完整步骤。实际实施、根因确认和代码变更必须有执行/检查证据；授权执行、PR或发布作为后续独立模块，模型 API 凭据不授予执行权限。

各岗位Agent输出不自动成为公共知识。相互交接需求基线、交付项、问题单等有版本对象，避免无出处摘要在岗位间传递后成为事实。

### 5. 最后统一优化类别（K14/K25）

与第一阶段开发主线分开排期。K14 集中处理检索基线、召回/排序/分块、上下文和成本时延；K25 集中处理提示词、正文/方案质量、交互工作流与整体性能成本。建立样本和前后对比后实施，不能提前声称效果提升。第一阶段原功能的正确性验收及阻塞缺陷修复保留在原任务中。

公司模型代理、员工模型授权、配额用量和公司对话管理为独立项目，不属于本项目接手清单或开发前置。

## 每个模块的统一交付要求

- 范围与前置：对应看板编号、业务输入输出、确认人、资源权限和外部动作。
- 实现与配置：实际代码/接口、数据模型、依赖锁定、幂等/失败策略及可关闭方式。
- 自动化或静态检查：仅报告本次真正执行的结果；文档检查不称作应用测试。
- 真实验证：区分模拟、真实模型、真实客户端、真实外部服务、人工业务与生产验收。
- 事实与引用：结论有来源、版本适用、无证据保留缺口，不能把相关度/质量分当真实性。
- 发布与恢复：异步派发后读取最终状态，记录未解决项，数据/通知/模型尝试去重，说明必要迁移与回退。
- 文档同步：按项目记忆在同次迭代更新01、02及相关03/04/05、实际验收、唯一看板和入口。

## 仓库与运行资料

真实客户材料、运行数据库、生成业务文件、个人客户端配置、密钥和完整业务对话不进入公开仓库。示例只用占位域名和非敏感数据；临时检查文件放tmp。当前代码支持的本机导出路径与未来授权下载链接要分别说明，不能假称远程服务已接通。

MCP指引、Agent提示词和模型供应商参数都不是操作系统/资源权限边界。权限由对应服务执行，Web/文件中的指令视为资料，不允许改变工具授权。

## 状态收尾

已完成只指实际约定范围。产品文档、开发文档和看板状态必须能在代码与实测中找到依据；本地验收不等于公司生产。下一迭代先检查[项目记忆](项目记忆.md)和看板，避免沿用过时压缩包基线、旧双MCP部署或未验收客户端假设。
