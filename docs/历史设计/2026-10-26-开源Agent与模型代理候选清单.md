# 开源 Agent 与模型代理候选清单及评估维度

版本：1.0｜评估日期：2026-10-26｜评估范围：GitHub 上可自托管开源项目；只考虑中国境内部署与国产模型。

本文根据公开仓库、文档和代码说明整理候选与比较维度。当前阶段只做规划和列选型，不决定最终采用，也不安装、部署或联调候选项目。待相关模块真正进入开发时，再按当时的需求、客户端版本、身份体系、部署约束和许可进行验证定案。采用原则是优先复用开源产品，项目自研只补齐公司业务数据、权限和流程缺口。

## 1. 候选清单

| 能力 | 候选方案 | 现阶段判断 |

## 2. Agent 框架候选与当前项目的适配

AgentScope 仓库目前列出的能力包括 Agent 工具/MCP、RAG 上下文、记忆中间件、权限与人工确认、持久化、多租户多会话 Agent Service，以及连接飞书和自定义 IM 的 Channels。项目使用 Python，仓库的 `pyproject.toml` 标注 Python `>=3.11` 与 Apache-2.0；当前知识蒸馏项目的 Python 3.12 环境在版本范围内。其服务示例包含飞书渠道和 Agent/RAG 服务，可作为起点。

若后续选择 AgentScope，可按以下边界适配：

1. 将 AgentScope 用于服务和渠道接入、会话上下文、MCP 工具和消息流。
2. 通过 MCP 调用本项目现有知识工具 `search_knowledge`、`read_knowledge`、`search_product_materials` 等；不把 AgentScope 自带 RAG Service 当作现有知识库的替代品，也不重新复制文档索引。
3. 商机、客户、需求候选、人工确认、销售活动、下一步和周报等事实继续由本项目结构化业务服务保存；AgentScope 会话/记忆只保存经定义允许的上下文，不是正式销售事实账本。
4. 售前 Agent 实际启动时，按员工身份映射、私聊与群 @ 路由、群权限、会话恢复、人工确认时重新鉴权、现有 MCP 流式/工具调用、国产模型接入、状态持久化和失败幂等比较候选。
5. AgentScope 2.x 在仓库中标为 Beta，LangGraph 当前已在依赖清单中。启动相关开发时按相同业务流比较版本成熟度、持久化、身份隔离、人工确认和现有 MCP 集成，再确定单一框架。

项目本地/云端依赖清单已有 LangGraph 锁定版本，但当前业务应用未发现 LangGraph 调用，依赖存在不代表 Agent 已实现。AgentScope 尚未添加到依赖清单。

## 3. 模型代理候选与当前项目的适配

New API 是目前比较接近“下载部署即可提供团队模型入口”的候选。仓库提供 Docker 快速启动和网页初始化；正式使用时仍须配置有授权的国产上游、模型、渠道和员工 API Key。若公司只要求统一模型入口、员工独立 key/额度和请求用量统计，它可以承担大部分现成网关功能。其说明面向应用、Agent 和团队提供自托管 AI 网关；可接入 DeepSeek、通义千问等国产服务，提供统一客户端入口、模型/渠道路由、API key、模型限制、额度、用量/成本统计和调用日志。公开 API 清单包含 OpenAI Responses 格式，适合作为 Codex 等客户端的候选协议入口。网关按员工账号发放 New API 凭据，上游国产模型密钥由服务端保存。

若公司要求管理模型调用正文，New API 不能直接覆盖 K22 的完整公司对话档案需求：公开功能文档描述的 Usage Logs 主要是请求归属、模型、Token、时延、费用、状态和路由信息；项目中关于记录 prompt 的请求仍是关闭/未计划状态。故应区分：

- **使用量和调用审计：**将 New API 列为一个候选。
- **托管 Agent 的工作对话：**由所选 Agent Service/本项目销售业务服务按访问控制、客户/项目关联和留存策略保存。
- **个人 IDE 客户端的完整输入/输出正文：**New API 当前不视为已具备。K22.2–K22.3 要先明确正文是否采集、谁可见、保留期及脱敏，再评估轻量插件/旁路存档/客户端主动上报；不应直接维护大型网关分支。若正文不采集，产品应明确仅管理用量与元数据。

New API 采用 AGPL-3.0。仓库可免费自托管，但若修改并通过网络向用户提供服务，需按许可义务审查是否要向交互用户提供对应源代码。实际部署或改造前核对许可义务。New API 自身的账号目录与公司企业身份/组织架构不是天然打通，需验证 SSO 或通过现有人员身份服务适配；分配 Key 时必须记录不可由客户端伪造的员工主体。

模型代理实际启动开发时，可按以下顺序验证：国内供应商单渠道 → 员工 A/B 独立 key 与配额 → OpenAI-compatible Chat → Responses 原样流式/工具调用 → WorkBuddy/Codex/Harness 的确切版本组合 → 账单与重试/断流差异 → 日志正文边界与管理员访问。

## 4. Higress 位置

Higress 仓库采用 Apache-2.0，并提供 AI Proxy 插件、国产提供商适配和 AI Statistics 可观测插件，涵盖 token、时延、指标/日志/trace。它更适合公司后续需要统一管理服务/API 入口、较高流量、Envoy/Kubernetes 运维体系已具备的场景。它不是即插即用的“员工模型账号和业务对话平台”；若选择它仍要建设个人身份、key 管理、费用归集及会话管理控制面。它与 New API 都保留为网关候选，按未来运维能力和员工使用流程比较。

## 5. 范围边界与必须自有的业务模块

开源 Agent 框架能承载对话、工具、会话、消息渠道和状态；它不能替本公司决定“什么算销售事实”。项目自有部分仍包括：

- 公司服务/产品能力目录和有出处的产品/项目检索连接。
- 客户、联系人、商机、阶段、客户原话、需求候选及逐条确认。
- 销售活动事件、沟通次数的口径、下步责任人与日期、提醒及撤销。
- 事实版本、来源文件/消息、用户确认、写入审计和周报快照。
- 员工/部门/客户/项目访问控制、渠道主体映射和公司对话保留策略。

这部分属于业务应用，不重复造模型代理或 Agent 通用循环。
