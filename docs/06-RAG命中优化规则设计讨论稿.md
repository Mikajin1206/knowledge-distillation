# RAG 命中优化：讨论结论与开发看板

版本：0.5
更新日期：2026-10-20
状态：已确认结论进入开发看板；未确定方案列入后续事项。本文记录目标要求，不表示代码已经实现。

## 1. 目标与执行边界

沉淀有来源、可复用的项目知识，提高售前等应用的证据命中质量，控制上下文长度和重复 token 成本，并保证流程图、系统结构图等资料可完整读取和复原。

- 知识采集覆盖项目全生命周期。售前是首个应用场景，不以售前问题筛选材料。
- 上传只保存原件及归属信息，不自动触发蒸馏或正式 RAG 入库。
- 沿用当前项目的 Word 蒸馏边界，不在本次优化中扩大文件类型范围。
- 评分不等于审核通过；只有审核有效并正式发布的知识进入正式 RAG。
- 本轮只更新讨论文档。现有代码、模板、Skill 和交接文档仍需按看板逐项核对和修改。

## 2. 已确认的设计结论

### C01：事实进正文，文件头按固定字段提取

产品范围、模块范围、公司实施范围，以及背景、问题、方案、方法、结果、适用边界等业务事实，均属于知识正文，应进入正文检索。不得因为这些事实也适合用于筛选，就把对应章节移出正文。

生成 MD 时，按照预先确定的文件头字段，从原文件和已整理的事实中提取对应值。文件头是事实的筛选信息，不代替正文的完整说明。例如：产品范围在正文中完整描述；已有 `products` 字段则提取其中的产品名称填入文件头。

不因为正文出现一个概念就增加一个文件头字段。`products` 是当前已有字段，按材料中确认的产品范围提取；产品范围和模块范围的完整事实仍写在正文。暂不新增 `modules`、`product_version`，也不把组织范围扩成文件头字段。未知或缺乏依据的字段不猜填。

### C02：评分写入文件头

生成的 MD 文件头必须包含综合质量评分，便于直接查看知识质量。沿用既有 `quality_score`，取服务端计算的加权综合分（0–100）；不另起一套重复字段。评分规则版本、覆盖率、分项得分和证据仍留在 sidecar/质量报告，不扩充 MD 文件头。

- 文件头评分与质量报告、sidecar 中的同一版本评分一致。
- 分项评分、覆盖情况、评分规则版本等按已有字段契约处理；详细证据和处理记录保留在质量报告中，不因本结论随意扩展文件头。
- `quality_score` 是评分引擎按当前权重计算的总分。当前引擎会将未提供有效分数的客户端维度记为 0，并在质量报告中标为 `unassessed`；因此文件头总分必须与 sidecar 中的覆盖率、分项状态和 flags 一起解释，不能把总分单独当成完整度或审核结论。这个现状不在 K01 改动，后续可基于使用反馈讨论展示方式。
- 评分只用于质量提示和辅助排序，不替代发布审核，也不能压过相关性。

### C03：沉淀知识，不记录项目进度

不增加“项目当前进度/项目当前状态”等管理字段，也不根据旧文件推断项目今天的进度。文档反映的是形成当时的信息，知识沉淀不承担进度台账功能。

与知识理解直接相关的原始事实仍保留，例如某方法的适用条件、材料明确写出的限制或尚未验证的结论，避免截取后改变含义。这不等于跟踪项目进度。

知识自身的审核、发布、撤回等系统状态与项目进度不同，继续沿用既有发布规则；其接口和版本细节见后续事项。

### C04：正文与生成过程信息分开

新版 MD 正文只承载业务知识。生成过程的证据映射、处理记录、识别复核记录、模型推断及其可信程度、审核与发布引用等信息，保留在质量报告、JSON sidecar 或服务审计记录中，不再作为 Markdown 正文章节生成。

正文可以保留必要的简短来源引用，详细来源映射不整表写入语义正文。原材料本身的冲突、限制和证据缺口如果影响知识适用性，应在正文明确体现，不能连同生成日志一起删除。

内容用途由信息本身决定，不由标题文字、标题层级或表格/清单形式决定。业务事实无论位于一级、二级或更深标题之下，均保留在正文；不同层级不得因分类不一致而被误删。过程记录不应靠章节标记藏在正文里，而应直接进入 sidecar、质量报告或服务记录。

章节路由只保留 `body` 和 `exclude`：`body` 用于正文分节与检索；`exclude` 用于显式标记不应进入知识产物的内容。新版不再使用 `metadata` 或 `audit` 作为章节路由类别。固定文件头字段仍按 C01/C02 生成；质量、来源与过程信息则由 sidecar/服务记录承载。文件头元数据与章节路由是两回事。

旧版 MD 按历史草稿保留，不原地自动改写。当前正式 RAG 发布尚未交付，因此旧 MD 不需要索引迁移；后续要入库时，优先从原件按新版规则重新蒸馏。原件不可用时，由人工逐节复核后生成新修订。旧 `metadata`/`audit` 标记在新版校验中视为旧路由，不能按标题自动转成 `body` 或 `exclude`；未复核的旧产物不得入库。这样既避免把旧标签下的业务事实漏掉，也不把处理记录误送进正文检索。

### C05：项目归属来自上传交互，由项目经理最终确认

项目名称必须由项目经理在引导式上传过程中提供，作为该批材料的项目归属。生成 MD 时沿用最终确认的名称，不由语义分析自动改写。

1. 上传交互根据输入名称检索库内相近项目名称，并展示候选名称。
2. 项目经理确认是否属于同一项目，系统不能仅凭相似度自动合并。
3. 若是同一项目，使用库内已有名称，再展示“本次使用项目名称：××”，由项目经理再次确认。
4. 若不是同一项目，保留项目经理确认的新项目名称。
5. 项目名称未提供，或相近名称的归属尚未确认时，不进入后续正式上传处理。

公司实施范围可能包含多个组织，这些组织仍是正文里的范围事实，不代替文件的 `project` / `project_name` 归属。正文提到其他项目时可以提示异常，不能自动新建项目或改变归属。

相近名称检查优先复用现有库内能力；是否需要补接口，要核对当前服务后决定，不预设建设一套复杂项目主档或单独查询接口。

### C06：可复原图形必须完整保存，后续不得有损压缩

增加一种受保护的资料类型，承载由核心图片识别、蒸馏形成的可复原流程图、系统结构图等。类型名称、具体格式和存储方式待设计，但以下要求确定：

- 完整保留已确认的节点、角色、连线、方向、条件、分支、并行、回环、起止等结构关系，以及必要文字，不用一段摘要替代完整图形资料。
- RAG 入库、切片、上下文整理和应用阶段都不得有损摘要、截断或拆散后丢失结构关系。
- 检索可以使用简要介绍和引用发现该资料；需要使用或复原时，必须按引用读取对应版本的完整内容。
- “不压缩”指不损失内容和结构信息，不限制可逆的文件压缩或传输方式。
- 保留原图及原文件版本、页/图定位、识别结果和未确认之处。识别不完整时不能声称已忠实复原。
- 资料过大时采用分步处理或单独读取，不能为适配 token 预算静默截掉完整结构。

将“正文介绍 + 完整受保护资料 + 过程复核记录”分别组织，是目前的建议方案，具体表示方式列入后续事项，尚未确定必须采用 JSON、Mermaid 或其他格式。

### C07：分节负责发现，完整 MD 按需读取

每个分节都关联对应完整 MD 的引用，保留标题路径、章节定位和版本信息。完整 MD 不重复复制到每个分节记录中。

分节命中不自动读取并注入全文。完整 MD 是否需要独立向量库或摘要索引，不作为当前开发前提，后续用测试确定。

| 检索后的情况 | 处理规则 |
|---|---|
| 分节已包含回答所需事实和必要前提 | 使用分节上下文 |
| 缺少可定位的前提、限制或关联步骤 | 先补读同主题内容或明确相关章节 |
| 需要理解整体方案、跨模块关系，或核对跨章节冲突，且局部章节不足 | 按需读取完整 MD |
| 多次局部补读仍有必要证据缺口，且相关内容可能在同一份 MD 中 | 读取全文核对 |
| 只是结果少、分数低，尚未找到相关文档 | 调整检索，不盲目展开全文 |

全文调用应说明当前证据缺口或整体核对目的。读取后只把回答需要的证据送入生成上下文；受保护图形资料按 C06 完整处理。

### C08：限制的是进入模型的内容，避免重复读取与注入

服务器读取一个完整文件，不等于必须把全文送给模型。服务端可以读取完整文件以定位章节，工具只返回被请求的内容。

- 默认返回命中分节、标题路径、来源和全文引用，不附带全文正文。
- 同一轮中，同一份 MD 的同一版本原则上只完整获取一次；后续复用已取得的内容。确需重取时记录原因，不能静默重复。
- 多个分节命中同一 MD 时先按文档和版本去重，不能对每个分节分别注入一遍全文。
- 提供可配置的候选数、单次返回长度、总证据预算和全文读取条件；具体数值后续调优。
- 超出预算时缩小读取范围或分步处理；不能静默截断事实条件或受保护图形。
- 记录检索轮次、读取范围、全文调用原因、返回字符/token 估算和重复读取，支撑后续优化。

## 3. 开发优先级与执行顺序

### K01 已完成：最小文件头契约

本项核对了 `src/ckp/md_render.py`、`src/ckp/quality.py`、`templates/蒸馏规范/评分权重.json`、当前项目模板及接续文档。当前渲染器允许的头字段多于实际生成时需要的字段；导出会把部分任务过程字段、项目阶段和项目主档标签一起带入 MD。K01 先固定目标契约，删除或迁移旧字段由 K03 实施。

| 字段 | 是否进入文件头 | 来源与规则 |
|---|---|---|
| `knowledge_id` | 是，必填 | 服务端分配的知识稳定身份 |
| `revision` | 是，必填 | 服务端生成的知识修订号 |
| `title` | 是，必填 | 本知识条目的标题 |
| `knowledge_type` | 是，必填 | 受控知识类型；采用现有分类，不在 K01 扩词表 |
| `project_id` / `project_name` | 是，必填 | 上传交互中由项目经理确认；名称采用复用/确认后的规范名称 |
| `status` | 是，当前草稿为 `draft` | 知识发布状态，不是项目进度；正式审核/发布状态以服务端记录为准，不能信任 MD 自报 |
| `products` | 是，按需填写 | 取自原文件确认的产品范围；只填现有字段需要的产品名。正文保留详细产品和模块范围，不因填头字段而删正文 |
| `quality_score` | 是，必填 | 取 `quality_check.weighted_score`，即服务端按当前任务评分权重计算的 0–100 综合分；沿用评分结果，不由模型另写一份 |
| `content_hash` | 是，必填 | 服务端对正文原始字节计算的 SHA-256；只证明正文未变化，不代表事实正确 |

以上字段为 K01 的最小文件头目标。字段值为空或原材料不支持时按字段规则省略或明确未评，不猜填。评分分项、评分规则版本、评估覆盖、证据、标记、缺口和详细来源映射留在 JSON sidecar/质量报告。

**不进入最小文件头的现有字段**：`stage`（项目阶段/进度分类）、`owner`、`task_id`、`rules_version`、`model`、`created_at`、`quality_score_version`、`topics`、`industry`。其中任务、模型、规则、创建时间及详细评分信息属生成或审核过程，留在 sidecar/服务记录；`stage` 不作为项目进度沉淀；`topics`、`industry` 当前没有确认的最小字段需求，不自动扩充头部。若后续评测证明某项筛选确有必要，再单独讨论。

当前代码还从项目主档填入 `products` 与 `industry`，并把 `stage`、`owner` 等字段写进 MD。目标契约要求 `products` 改为从材料中已确认的产品范围提取；这是 K03 的实现差距，不在 K01 改代码。

文件头示例（`products` 仅在材料明确时出现；评分值示意）：

```yaml
---
knowledge_id: "k-example"
revision: "1"
title: "某项目采购与库存方案"
knowledge_type: "项目方案"
project_id: "p-example"
project_name: "上传时由项目经理确认的项目名称"
status: "draft"
quality_score: "82.5"
content_hash: "<正文 SHA-256>"
products:
  - "材料中确认的产品名称"
---
```

`render_frontmatter()` 当前将标量写成带引号字符串，因此示例保持现有导出格式。K03 可在维持格式兼容的基础上按契约收敛字段。

优先级：P0 先统一产物和上传交互；P1 接续索引、读取及应用；P2 用真实问题调优。下表是开发顺序，不表示已有功能全部缺失；每项先核对现状，再补齐差距。

## 6. 给开发的执行要求

1. **先核对、再补差距。** 本文是新的目标要求；当前代码并未在本轮重新验收。不要把现有标签、字段或单次演示当成目标已完成。
2. **先统一输出契约，再改下游。** 按 K02 结论核对 `docs/05-上传蒸馏与MD产出交接文档.md`、项目 Skill、模板、蒸馏指引、导出、sidecar 和索引适配器，避免提示词已改而解析器仍按旧规则排除正文。
3. **固定文件头，评分入头。** 复用已有字段与评分，正文中的产品/模块/公司范围完整保留；头部只提取既定字段需要的值，不堆砌新字段。
4. **项目归属由人确认。** 必填项目名；相近名称只给候选；同项目复用已有名字并再次确认；模型不自动合并、改名或替换归属。
5. **过程记录不污染知识。** 生成日志、详细质量记录、模型判断可信度等与检索正文隔离；来源引用和影响知识适用性的真实边界继续保留。
6. **完整资料可追溯。** 分节保留完整 MD 引用和版本、来源定位；本地路径只有在运行环境可达时才可读取。跨主机读取方式核对服务后落实，不把保存了路径当作接通。
7. **命中分节不自动展开全文。** 默认只返回命中内容和引用；先补章节，再按证据缺口读取全文。服务端内部读取完整文件时，也只向模型返回所需内容。
8. **控制重复和 token。** 对同文档同版本去重，缓存已取得内容，配置证据预算；提供读取原因、返回长度和重复调用日志。不能把多份全文无条件并行注入。
9. **保护图形完整性。** 受保护资料的每个处理环节都必须遵守完整保存、完整回取要求；不能只在生成时贴一个标签就认为下游已受保护。
10. **不绕过既有审核发布。** 草稿输出、评分完成、路由有效都不代表获准进入正式 RAG。项目进度字段精简不影响既有审核发布约束。
11. **验证与风险相称。** 对实际变更做对应检查：字段一致性、业务事实未被误排除、上传确认交互、图形复原、按需读取和 token 统计。区分自动检查、真实服务/客户端调用、人工内容复核及未验证项。
12. **完成一项标记一项。** 每个工作包交付后更新本看板，不一次性把整组任务标为完成。涉及未定事项先把方案写回本文，再按确认后的方案实施。
