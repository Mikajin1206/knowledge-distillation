# Knowledge Distillation：需求规格

版本：1.0；更新日期：2026-10-22。本文定义产品目标与未来能力边界。当前已实现范围和后续工作状态以第 8 节及当前代码契约与接续文档为准。历史测试报告、过程记录和客户文件不纳入公开仓库。

> 业务基线：按项目全生命周期收集通用知识；原件保存、知识蒸馏、审核发布和 RAG 应用各自分层。售前是首个应用角色，不是材料采集的筛选条件。

## 1. 背景与目标

原始文件类型繁杂，统一自动处理成本高，内容质量不一，给检索带来噪声。完全不处理又会使图片、流程图等内容难以按业务语义使用。

本项目将文件保存、知识生产、知识应用分开。公司文件完整保留；只有选择、蒸馏、审核后的知识进入 RAG。项目总结工程前移到材料整理阶段，随项目各阶段持续形成知识。

首个应用是售前。未来支持运维问题检索、实施解决方案与案例检索、实施方案生成。通用知识按项目全过程形成，岗位专用抽取由各 Agent 负责。

## 2. 已明确的业务边界

1. 保留原件上传能力，负责将原件保存到配置的文件适配器并关联项目、行业、产品、项目经理等标签；当前只实现本地适配器，公司文件服务器接入仍是目标。
2. 上传成功不触发全量解析、视觉处理或 RAG 入库。原件不因无法解析而丢失。
3. 知识蒸馏能力以《templates/蒸馏规范/阶段材料清单.md》定义的六个项目生命周期阶段作为 RAG 主分类，引导用户按阶段选择和补充材料；`knowledge_type` 仅作为文档类型补充属性，不能限制六阶段覆盖。
4. 客户端模型与可用工具执行整理、图像理解和流程复原，MCP 维护来源、任务、规则版本和结果。
5. 项目经理审核知识的具体版本。当前开发版可在本地记录审核，并发布到本地 RAG 开发沙箱；公司服务身份认证和生产发布仍未实现。
6. RAG 接收统一知识正文及来源、资产引用，不再承担任意原件的识别和修复；仍负责校验、切分、索引和版本管理。
7. 不强制每个项目少于十份。以少量核心知识组织项目，必要的问题案例、操作步骤和技术细节可以独立成篇。
8. 原件库支持名称、标签、项目和版本查找；未经蒸馏的图片不承诺按图内业务含义命中。

## 3. 用户及职责

| 角色 | 职责 |
|---|---|
| 上传人员 | 保存原件，选择项目，补充可确认的标签 |
| 项目整理人员 | 按阶段关联材料，执行蒸馏，补充缺口，处理冲突 |
| 项目经理 | 核对事实、完整性、适用范围，审核具体知识版本 |
| 客户端 Agent | 读取规范，执行工具和生成，提交草稿与引用，调用发布 |
| 公司 MCP | 管理原件引用、审核记录、正式发布、知识检索与来源读取 |
| 蒸馏 MCP | 管理阶段任务、提示词、标准、材料覆盖和草稿，不自行批准知识 |
| 售前／实施／运维 Agent | 根据任务从通用知识检索、抽取、组织输出 |

## 4. 业务主流程

### 4.1 建立项目与保存原件

建立稳定项目 ID，维护项目名称、行业、产品、项目经理和可补充标签。项目未完成分类时允许暂存，发布前补齐必要元数据；项目经理等责任字段不得由正文猜测。

用户可逐个或批量上传。文件服务返回稳定文件 ID、版本 ID、哈希、名称、类型、大小。记录上传人、时间、来源别名、项目关系与可确认的项目阶段。上传后可查询原件并按指定版本读取。

相同内容按哈希复用存储的前提是符合现有文件服务权限和存储规则；不丢弃不同项目、上传记录、文件名与版本关系。无法确认版本时保留为待确认关联，不自动覆盖。

本机路径仅适用于本地客户端适配，不作为远程 MCP 的默认上传方式。远程上传支持客户端传输或文件服务上传凭据／上传会话；大文件不强制通过 base64 整体塞入 MCP 参数。具体传输方式在 P1 核对现有服务后确定。

### 4.2 按阶段建立蒸馏任务

用户选择项目和阶段；工具列出材料清单、模板、提示词、质量标准及可用能力要求。已有文件通过 ID 与版本引用，不重复上传。允许跨阶段材料、批量关联、补充上传、缺失声明和中断恢复，不强迫用户一次交齐。

| 阶段 | 知识范围与典型材料 |
|---|---|
| 立项与范围 | 项目背景、目标、合同范围、交付边界、约束、立项资料 |
| 调研与需求 | 现状流程、角色、需求、需求确认、业务规则 |
| 方案与设计 | 业务流程、架构、功能、接口、数据关系、设计取舍 |
| 实施与变更 | 配置、迁移、集成、操作步骤、变更原因、问题解决 |
| 测试与验收 | 测试场景、缺陷修复、验收结论、实际交付范围 |
| 运维与改进 | 环境版本、故障现象、诊断、根因、处置、验证、改进 |

阶段允许配置，缺失材料记录缺口，不因缺少某类文件自动认定项目不合格。合同、方案、报告优先作为来源，不按文件类型直接认定为事实正确或自动获准入库。

### 4.3 按需解析与知识蒸馏

原件库可以保存各类文件；蒸馏入口只接受标准 Word `.docx`、`.doc`。Excel、PPT、PDF、独立图片及其他格式只保存为原件，不做解析、不提供给本地模型、不参与知识生成。Word 外格式的蒸馏请求由 MCP 服务端拒绝，本地模型向用户解释并停止；混合选择时必须先询问用户是否仅用 Word 继续，不能静默跳过。旧版 `.doc` 用 LibreOffice 转为临时副本后解析，失败即停止该材料。

只读取本次任务选定的 Word 材料，通过临时副本调用解析能力。先处理关键材料，根据缺口补充，不遍历全部原件执行昂贵处理。Word 内嵌图片和流程图按需读取，记录使用工具、规则和模型版本及失败情况。

蒸馏保留场景、问题、约束、方法、步骤、选择原因、结果、适用条件和来源。区分合同约定、设计目标、实际实施、验收确认、人工经验与模型推断。数值保留单位、口径、时间及出处；无依据的成效不能补造。

输入材料存在冲突时并列记录来源与冲突，不让模型静默裁决。人工补充记录提供者、时间和审核结论；关键推断未经确认不能作为已验证事实发布。

维护“需求 → 设计 → 实施变更 → 最终交付 → 运维问题”的关联。阶段知识可逐步发布，明确适用版本、有效时间和是否已验证，不等待结项。

### 4.4 图像与流程知识

图像结果至少包含内容描述、来源文件与版本、页／图／幻灯片位置、必要资产引用和不确定项。流程图包含节点、角色、顺序、分支条件、异常路径；结构明确时输出可编辑流程表达。

区分忠实复原与整理建议；不能凭空间接近推断连接，无法确认的标记待核对。原图与复原图分别保存和关联。由用户核对图文关系后，描述随知识正文入库，图像资产保存在文件服务器。

稳定 ID 与版本作为持久引用，访问链接按需生成；临时路径和过期签名 URL 不作为唯一来源。重要来源定位到章节、页码、表格、图号或可用段落锚点。

### 4.5 草稿、审核与发布

草稿保存正文、元数据、来源清单、资产清单、质量检查、冲突与缺口。技术检查和人工审核分别记录。

建议状态：draft → in_review → approved → publishing → published。退回进入 changes_requested，修订形成新版本；发布失败记录 publish_failed，可对相同版本幂等重试。旧版本可标记 superseded 或 withdrawn。

审核绑定 knowledge_id、revision、正文及关联清单的内容哈希、审核人、结论、时间和意见。公司服务核验审核身份与项目责任关系，不信任客户端自报已审核。修改正文、来源或关键适用条件后重新审核。

发布前确认审核有效、来源和资产可回取、必要元数据完整、没有被当作确定事实的关键未确认项。无关缺口可以显式保留，不阻塞已独立核实的知识；知识不得声称覆盖缺失内容。

审核通过不等于已经索引。公司 MCP 创建发布任务，保存不可变版本，完成切分与索引读回后才标记 published。新版本成功切换前继续提供原有效版本；部分失败不暴露半套新知识。重复发布不产生重复知识块。

默认检索当前有效、已发布版本。历史知识保留追溯入口，不与当前版本混在默认结果。撤回后停止默认命中；原件和审核记录仍保留。

### 4.6 应用 Agent 使用

售前 Agent 负责抽取行业需求、解决方案、交付案例、成果和能力边界。实施 Agent 负责检索设计、配置、操作和案例并组织实施方案。运维 Agent 负责现象、环境、版本、根因与处置检索。

各 Agent 使用同一通用知识层；生成物不是新的项目事实，不能自动回灌。需要纳入通用知识时重新走来源、审核和发布。

## 5. 知识范围与结构

核心知识可按项目阶段或明确主题组织；独立问题案例按主题关联。避免为凑数量压缩必要步骤，也避免将同一正文重复包装给多个岗位入库。

建议统一交付为 UTF-8 Markdown 正文加结构化清单。字段至少包括：

- 知识身份：knowledge_id、revision、content_hash、title、knowledge_type。
- 业务上下文：project_id、行业、产品、阶段、主题、责任人。
- 适用性：系统／产品版本、环境、时间、前提、限制、事实状态。
- 正文：背景、问题、约束、流程／步骤、方案与理由、结果、相关知识。
- sources：file_id、version_id、sha256、位置、支持的正文段落；支持一条知识对应多个来源。
- assets：资产 ID／版本／哈希、类型、描述、原件定位、复原性质与不确定项。
- 人工补充、冲突、缺口、处理工具与规则版本。
- 审核引用、发布状态和替代／撤回关系；审核与发布由服务管理。

标签由项目上下文继承，允许人工修正；行业和产品支持多值。标签用于筛选和关联，正文承担业务语义。细粒度字段与校验规则在 P1/P2 固化。

## 6. MCP 设计边界

以下为拟定职责，不代表现有接口已支持。

| 服务 | 建议工具 | 输入／输出重点 |
|---|---|---|
| 公司 MCP：原件 | upload_original、register_original、search_originals、get_original | 上传或登记可核验服务回执；返回稳定文件引用及保存状态，不含 index 开关 |
| 蒸馏 MCP | start_distillation、get_stage_guidance、attach_sources、get_distillation_task | 项目、阶段、材料引用、清单、提示词／规范版本、缺口、任务状态 |
| 蒸馏 MCP | submit_distillation_draft、submit_visual_result | 草稿、来源映射、资产、处理记录；返回版本和检查结果 |
| 公司 MCP：审核发布 | submit_for_review、record_review、publish_knowledge、get_publish_task | 服务保存的版本与审核记录；返回审核或索引真实状态 |
| 公司 MCP：应用 | search_knowledge、read_knowledge、resolve_source、get_asset | 返回正文、版本、适用性、来源与有效状态；支持全文及来源回取 |

蒸馏、公司文件、审核发布和 RAG 的逻辑职责独立，可按内部模块维护。WorkBuddy 等 MCP 客户端统一只配置一个 MCP server；各项能力通过同一 server 注册为多个工具提供，不为 RAG 或其他单项能力另配 MCP server。MCP 服务身份、启动入口和客户端配置保持唯一，工具按职责划分并返回各自真实状态。规范通过 MCP 提供，客户端检查工具和 skill 是否实际可用；缺少能力时返回缺口，不声称已经执行。模型供应商与参数沿用统一配置机制，不硬编码本轮测试模型。

## 7. 质量与验收

- 原件：上传后能按项目查找并回取指定版本，哈希一致；解析失败不影响原件保全。
- 分离：原件上传不创建知识候选、不调用模型、不写向量索引。
- 蒸馏：可以从未入 RAG 的项目开始；已存原件不重复上传；材料不足与冲突可检查。
- 图像：描述和复原有来源且经核对；清理临时文件后仍可回取图像。
- 审核：未审核、已修改或审核版本不匹配的知识无法发布。
- 发布：重复调用幂等，失败可恢复，新旧版本可正确切换，草稿和撤回版本不默认命中。
- 检索：真实问题能返回适用的知识与可打开的证据；无依据时明确没有证据。
- 运维：能看到任务状态、逐项错误、处理记录和重试结果，异步派发不是完成。

试点同时覆盖售前、实施、运维问题，固定问题与期望证据后再检索。记录 top-k 命中、无关结果、答案引用正确性、版本适用性、整理与审核时间。阈值在试点问题集建立时确定，不预先声称命中率提升。

## 8. 当前实现状态与后续范围

已通过 WorkBuddy 验收的 MCP server 版本为 **1.2.1**，单一服务暴露 **30 个工具**（原有 21 个，加本地 RAG 开发工具 9 个）；**1.3.0** 在同一服务增加 `metadata_catalog`，共 31 个工具。WorkBuddy 已验收 OA 产品/领域选择写入、独立审核、65/65 分块发布与 RAG 正反向筛选；项目完整自动化测试 138 项通过。`CKP_LOCAL_ACTOR` 与 `CKP_REVIEWER_IDS` 绑定本机 `local_development` 身份；本地文件适配器为 `local_versioned_store`。本地已有审核记录、异步发布任务、逐块读回校验，以及图形 JSON 的独立版本上传与读取。撤回及部分负向输入仍未做 WorkBuddy 黑盒验收；公司 file server、remote auth 和生产发布仍未实现。本节将产品目标与当前交付分开陈述。

### 当前已实现

- 原件上传与本地内容寻址存储：支持项目元数据、标签、版本、上传记录和哈希校验；上传不解析、不调用模型、不索引。
- 知识蒸馏：MCP/CLI 按六个生命周期阶段管理任务；只允许 `.doc` / `.docx` 进入蒸馏；材料版本固定；缺口、人工补充和规则快照留痕。
- Word 处理：按需读取正文、表格和内嵌图片；非 Word 文件只保留原件并由蒸馏入口拒绝；相关图片由客户端多模态模型理解，服务端不做 OCR 或视觉推理。
- 评分与产出：评分权重可人工维护，任务固定权重快照；低分不阻断草稿；导出 Markdown 与 JSON sidecar，支持正文哈希验证和任务临时文件清理。章节路由只支持 `body`/`exclude`；旧 `metadata`/`audit` 标记不会自动转换。
- 本地 stdio MCP 与 `knowledge-distillation` Skill 已实现。1.2.1 主链30工具验收通过；1.3.0产品线/领域metadata_catalog契约已恢复，本机验证通过，待WorkBuddy验收。发布读回、图形资产和本地 RAG 的具体边界见 docs/05 与 docs/07。

### 已验证与未验证边界

- 当前状态和验证证据以 docs/07 为准：1.2.1主链自动化套件125项通过；真实 Qwen 请求返回 1024 维；协议预检确认 30 个工具、空列表和路径脱敏。2026-10-22 WorkBuddy 已完成1.2.1主OA单版本发布、检索、图形读取及目录定向复测；1.3.0产品线/领域契约本机验证通过，待WorkBuddy验收，撤回黑盒仍未执行。
- `local_versioned_store` 和 `local_development` 只证明本机开发能力。公司文件服务器、远程认证及生产发布尚未实现；本地自动化或协议预检不能证明这些外部集成已接通。
- MCP instructions 是模型工作指引，不等同于操作系统权限隔离。

### 后续工作顺序

1. **完成当前版本的最小真实客户端复测：**加载最新 MCP/Skill，保留现有草稿与审核，以六阶段路由重试同一 publish_task，再用隔离 Word 与非 Word 材料验证工具顺序、混合选择确认、图片排除、首稿评分、哈希与临时文件清理。
2. **对接公司文件服务：**先取得真实接口、权限和错误契约，再替换本地存储适配器；核验指定版本读取、SHA-256、链接刷新、资产引用和清理。
3. **实现项目经理审核门：**审核绑定 knowledge_id、revision、正文及来源/资产哈希；版本任何相关变更都须重新审核；服务端核实审核身份。
4. **接入公司 RAG：**只发布已审核且有效版本；遵守 docs/05 的切片、元数据、哈希、幂等、版本替换、撤回和读回要求。
5. **开发售前、实施、运维 Agent：**按 docs/05 的固定问题集和引用、事实状态、适用性及不回灌标准分别验收。
6. **生产部署与迁移：**多人权限、备份恢复、任务隔离、监控和迁移在真实基础设施上单独验收，不把本机测试当生产验证。
